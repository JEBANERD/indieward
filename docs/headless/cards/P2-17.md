# P2-17: MCP tools for `watch` and `traps inject`, with explicit consent

## The Job
`indieward watch` (P4-01) and `indieward traps inject` (P2-09) are CLI-only. Add MCP tools to `src/indieward/mcp_server.py` so the plugin can offer them. Both have side effects the creator must agree to, so each tool is split into a **plan** step with no side effects and an **apply** step that needs the plan's confirmation code.

**Inject**
- `trap_inject_plan(project_dir, build_id, file, rows=False)`: calls `inject.inject(..., apply=False)` and returns the diff, the new keys and a `confirm_code`. The code is a short hash of (build_id, file path, file sha256, planned new text).
- `trap_inject_apply(project_dir, build_id, file, confirm_code, rows=False)`: re-plans, refuses unless the code still matches (so the file hasn't changed since the creator saw the diff), then calls `inject(..., apply=True)` (backup first, as today).

**Watch**
- `watch_plan(project_dir, sources)`: lists what each source would receive, without sending anything:
  - Software Heritage gets hashes only.
  - GitHub and npm get exact strings, shown by trap label. It also shows the actual strings, because they stay local in the conversation.
  - It returns the disclosure text and a `confirm_code` over (sources, the needle list).
- `watch_run(project_dir, sources, confirm_code, include_core=False)`: refuses without a matching code. For GitHub it reads the token only from the MCP server's own `GITHUB_TOKEN` environment variable; **never add a token parameter**, because tool arguments end up in transcripts. Otherwise it behaves like `watch.run`.
- `watch_leads(project_dir)`: read-only.

**Descriptions and skill**
- Each apply/run description says, in plain words, to show the plan to the user and get their yes before calling it.
- Add a short section to a plugin skill (`add-traps` for inject; `check-suspect` or `clone-response` for watch) describing that flow.

## The Why
Plugin users never touch the CLI. These two features are where consent matters most: one discloses markers to outside companies, and the other edits the creator's files. So the tools need to make the "show first, then act" step hard to skip.

## The Guardrails
- Everything in docs/headless/RUNNER.md.
- No tool sends email, submits forms or contacts stores. `watch` only queries the three official search APIs it already uses.
- The existing verification gate and `accept_disclosure` rules still apply. A confirm code from one plan can't authorise a different file, build, source list or needle set.
- Check `indieward-hook block-send` and the plugin tests still pass. Tool names must not contain `send`, `submit` or `email` (`tests/test_plugin.py` enforces this).

## Done Means
- Tests with recorded API responses, as in `tests/test_watch.py`. Nothing goes over the network.
  - Plan tools have no side effects (no file changes, no requests).
  - Apply/run tools refuse a missing, wrong or stale code (the file changed after planning).
  - `watch_run` never takes a token argument and reads `GITHUB_TOKEN`.
  - A good code performs exactly the planned change.
- `claude plugin validate plugin --profile directory --strict` passes if the CLI is available (otherwise list it under "Jasper by hand").
- `python -m pytest -q` passes. QUEUE.md row set to `in-review`. PR body written per RUNNER.md.
