# P3-07: Release workflow: first run on a pre-release tag

**Needs Jasper:** pushing a tag and approving a release are his calls.

## The Job
P3-02 (#32) added `.github/workflows/release.yml`. Only its build-only dry run has run ("build, test, SBOM" passed). The attestation, GitHub release and PyPI jobs have never run. #32 says they "run for the first time on the first real tag". Find out on a pre-release instead.

1. Before tagging, make sure a tag like `v0.1.3-rc1` creates a GitHub **pre-release**. `release.yml` triggers on `v*`, and on main (105bac5) nothing in it marks rc tags as pre-releases, so that probably needs a small PR first (for example `prerelease: ${{ contains(github.ref_name, '-') }}`, or `--prerelease` if it uses `gh release create`). The PyPI job already stays off unless the repo variable `PYPI_PUBLISH` is `true`; leave it unset.
2. Push the tag from `main`. Watch the run.
3. Check the outputs: the wheel and sdist are attached, the SBOM is attached, `gh attestation verify <wheel> --repo JEBANERD/indieward` succeeds, and `pipx install <wheel>` followed by `indieward doctor` works on Windows.
4. Fix any failure in a PR, delete the pre-release and its tag, and repeat. When it's clean, decide whether to set up PyPI trusted publishing (`PYPI_PUBLISH`) before the real `v0.2.0`.

## The Why
A release pipeline that first runs on launch day fails in front of users.

## Done Means
- One clean pre-release run with verified attestation, and a note in this card of what (if anything) had to change.
